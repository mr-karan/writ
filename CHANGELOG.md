# Changelog

Writ's notable changes, newest first. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/). Until 1.0, a minor version may change behavior.

## Unreleased

### Added

- `GET /v1/audit?changes=true` and `writ audit --remote --changes` leave out the reads: the rows of op `read` and `state-read`, and the requests by `GET` or `HEAD` that name no op and were allowed or needed no decision, such as `GET /v1/whoami`, a control UI page, and its static files. A refused request of no op, a sign-in, the server's start, and every change stay. Without it every row shows, as before. The audit page shows only the changes by default, with a Show reads link, `?reads=1`, that works with scripts off. See [Read the audit log](docs/audit-log.md#2-narrow-the-log-with-filters).
- Verified GitLab webhooks, so a push or merge reaches `writ serve` in seconds. A pinned `repo` block takes `webhook_secret_file`, and `POST /v1/hooks/{forge}/{repo}` takes the project webhook's push events. `writ serve` checks `X-Gitlab-Token` against the secret in constant time, or, when the file has a signing token starting with `whsec_` (GitLab 19.1 and later), the `webhook-signature` over the body and a 5-minute timestamp window. A delivery that passes only makes the poll read the default branch's head now, through the forge's read token. Its body is never parsed, so nothing in it is trusted, and it never plans or applies. A failed check gets 401 with the same words whatever the reason, and the audit row's `check` says which. Deliveries are bounded to 1 MiB, 10 a second from one address, and 5 a second for one repository. A resend with a `webhook-id` or `Idempotency-Key` acted on already gets 200 and is dropped. Each delivery writes an audit row of op `hook`, with no secret and no body. A repository with a webhook is polled every `poll_every_with_hook`, 5 minutes by default, as a backstop. `GET /v1/repos` and the Repositories page show `hook` and `hook_at`, the last delivery's time. Repositories added with `writ repo add` can't have a webhook. Migration 0018 adds `hook_at` to repos. See [Get changes in seconds with a webhook](docs/webhooks.md).
- `GET /v1/audit` and `writ audit --remote` read the audit log: newest first, by plan (with its approvals, run, and state writes), run, `stack@env`, person, operation, and time, in pages. A token sees the rows of the stacks it may read, and the rows of no stack only with `admin` on every stack in every environment. A filter of a stack the token can't read returns an empty page, the cursor is encrypted, and an approval across environments leaves one row for each. A refused row's reason, which can quote what its request sent, is withheld, a state write's reason is shown without the state's hash, and no row shows a client address or a nonstandard method.

- `egress_mode` and an env's `egress` list in the config. Under `report` or `enforce`, each OpenTofu run of `writ serve` gets a network namespace of its own with only loopback, and reaches the network only through Writ's egress proxy, which checks each host and port against the env's list before it connects. The proxy never connects to loopback, link-local, or metadata addresses, or to a NAT64 address of one, keeps a wildcard out of private addresses, and connects only to the address it resolved. The credential endpoint, with the run's token, and the state backend, on a rate limit of the run's own, reach the run on its own loopback. `enforce` refuses what the list lacks, and `report` lets it through. The provider install runs in a namespace of its own too, behind a proxy that allows only public addresses, and installs only from the registries that the new `provider_registries` lists, `registry.opentofu.org` and `registry.terraform.io` by default. Every run records each destination it asked for, the install's marked `install`, with its verdict and count, as `network` on its plan or run in the API and the control UI, and in a `run egress` log line. A refusal names the host, port, and the env's list in the failed plan's diagnostics. The default, `off`, leaves runs on the host's network as before. Migration 0017 adds the `network` column to plans and runs. See [Run isolation and egress](docs/run-isolation.md#egress) and [Egress](docs/serve.md#egress).
- Each plan says what started it: `started_by` is `person` for a person's session or the dev user, and `ci` for a CI job's token, in `GET /v1/plans`, `GET /v1/plans/{id}`, and `POST /v1/plans`. `GET /v1/plans?started_by=person` or `ci` lists only those; `drift` is refused, since drift checks aren't plans. `GET /v1/drift` gives each check `started_by` `drift`, and `every`, how often Writ checks each stack. It needs no migration: Writ reads it from the author stored with each plan.
- `writ plans --remote` lists the plans of an environment, newest first, with a `STARTED BY` column, and takes `--stack`, `--status`, `--started-by`, `--limit`, `--cursor`, and `--json`.
- `notify "NAME"` blocks in the server config send notifications to a Slack incoming webhook or to your own webhook, with an optional HMAC-SHA256 signature: a stack that drifts or is clean again, a failed plan or apply, an apply, a state written outside Writ, and a plan that needs approval, narrowed by `envs` and `stacks` patterns. Each message has the event, the `stack@env`, a summary in Writ's own words, who or what started it, and a link to its page; it never holds a secret, a plan body, or a diagnostic's text. Delivery runs on a bounded queue apart from plans and applies, retries a timeout or a `5xx` for about four minutes, sends only to the configured URL with no redirect, and caps time and size. `writ serve --check` lists each notifier with its delivery counts, `--notify-test` sends each a test message, and the Settings page has a Notifications card. Migration 0020 adds the `notification_status` table. See [Get notified](docs/notifications.md).
- The control UI has an audit page, `/ui/audit`, linked from the sidebar. It reads `GET /v1/audit` with the session, so it shows the same rows under the same rules: a person sees the rows of the stacks they may read, refused rows show `reason withheld`, and no row shows a state hash or a client address. Pickers and a form filter it by environment, stack, person, operation, plan, run, and time as GET parameters that work with scripts off, and Older entries pages with the API's cursor. Each plan's and run's page has an Audit trail button.
- A drift check has a page of its own, `/ui/drift/{ref}`: its head, its changes outside OpenTofu and in the code, or its error. A stack's Drift tab lists the checks Writ keeps, each linked, the Overview's drift alerts link the check, and `/ui/plans/{id}` of a drift check's plan redirects there. `GET /v1/drift/{id}` returns the check as `writ.drift-check/v0`, by its `ref` or plan id, to a token with `read` on its stack. `writ.drift/v0` gives each check its `ref`, and with `env` and `stack` lists the kept checks under `checks`.
- `writ mcp` has a `list_plans` tool: the plans of an environment as `writ.remote-plans/v0`, newest first, with the `stack`, `status`, `started_by`, `limit`, and `cursor` filters of `GET /v1/plans`.
- The control UI marks what started each plan, with a person or a CI icon in the plans list, the approvals, and a stack's Plans tab, and in words on the plan's page. The plans list has a Started by picker that works with scripts off. A stack's Drift tab heads its check `Drift check, every 6h`, with the configured interval.

### Changed

- A webhook delivery's audit row whose path names a pinned repository with a webhook shows to every principal that may `read` a stack of that repository, in any environment, not only to `admin` on every stack in every environment, so the team that runs a repository sees its own deliveries, passed or refused. Its `via` is `webhook of repository NAME`, and the audit page shows the repository as its target. A delivery to any other name still shows only to that admin. See [Read the audit log](docs/audit-log.md#prerequisites).
- A plan that changes nothing ends `no-changes`, a new status, in place of `approved`. It is a plan whose apply OpenTofu would find nothing in: each resource change a no-op that neither moves nor imports, no output that changes, and nothing changed outside OpenTofu. It never expires, keeps no saved plan, takes no approval, and never applies: `writ approve --remote ID` and `writ apply --remote ID` refuse it with HTTP 409 and class `state`, `plan ID changes no resource`. `GET /v1/plans?status=no-changes`, `writ plans --remote --status no-changes`, and the plans list's Status picker find it. After a merge whose newest plan of the merged sources is `no-changes`, `POST /v1/runs` answers 200 with `run` `null` and the plan's id, and `writ apply --remote --merged` says there is nothing to apply and exits 0, so the apply job passes; if a run applied to the `stack@env`, or its state moved, after the plan, it is refused with `state`. `writ approve --remote --pipeline` lists a pipeline's `no-changes` plans and approves the rest, and passes for a pipeline of only such plans. `writ apply --remote --yes` prints a `no-changes` plan and exits 0. The control UI shows it in a grey pill, with Approve and Apply marked not needed and no apply command. Migration 0019 lets the plans table hold the status, as a pair of files, one an engine, since SQLite cannot alter a CHECK; no row moves, so a live plan from before that changes nothing stays `approved` until it expires. See [A plan that changes nothing](docs/approvals.md#a-plan-that-changes-nothing).
- The control UI is redesigned: a sidebar with stack counts, every page set in cards with labels in one column, and no lines that say what a button does. A stack's resources group by service, module, or none, with a strip of categories and counts, a filter on address, type, and ID that works with scripts off, and rows that open to show the full ID, ARN, and region. A plan keeps its approval, apply, and facts in one head card, with Action and Risk pickers over its changes. Access no longer shows your own grants; Who you are does.
- A stack's resources read better on a real stack. A type's label writes its acronyms in capitals, such as `IAM role`, `LB listener`, and `ACL token`. Under a category or module heading a row shows the resource's name and key without its module and type, and the flat view and the opened row show the whole address. A long address breaks after `/`, `:`, `.`, or `[`. A row whose ID is its ARN shows the name the ARN ends with, and the opened row shows the ARN once. An opened row shows the provider without its registry host and the region from the index or the ARN. The module chip shows only off the root module.
- The control UI names the product Writ, and says `writ serve` only for the command. Access, Settings, and Repositories no longer say they are read from the config file.
- A `writ serve` with `provider_uids` marks itself not dumpable at start, because it holds state keys and secrets: no process of its own user can trace it or read its memory, and it writes no core dump. See [How providers are kept from the keys](docs/serve.md#how-providers-are-kept-from-the-keys).
- A plan that failed because its state has no secret set shows the explanation once, in the note with the adopt command. Its diagnostic is one short line. The plan's document is unchanged.

### Fixed

- A remote command that gets an answer it can't use, such as `writ` 0.1.5 meeting the 200 that `writ serve` 0.1.7 sends for a merged apply with nothing to apply, fails with an error that says so and names both versions, and with `--json` prints the command's failure document. Before, it could exit 1 and print nothing. Every answer of `writ serve` now carries `X-Writ-Version`, and a remote command warns once on stderr when the server is a newer release than `writ`: a newer major or minor version, or, before 1.0, any newer version. See [Version skew](docs/commands.md#version-skew).
- A retried apply job after a merge failed with `saved-plan: nothing to apply`, exit 1, when the first run had applied the merged sources. When the newest run on the `stack@env` applied a plan of the merged sources and the state hasn't moved since, `POST /v1/runs` now answers 200 with `run` `null` and that plan's id, as for a `no-changes` plan, and `writ apply --remote --merged` says there is nothing to apply and exits 0. If a version of the state on the `http` backend that the run didn't write came since, it is refused with `state`; after a newer run that failed, the apply is refused as before. See [Apply after a merge](docs/apply.md#apply-after-a-merge).
- A notification to a host whose TLS certificate Writ doesn't trust, or whose name doesn't resolve, was retried for four minutes as `connection failed`. It now fails at once, with `tls: ...` or `dns: no such host` as its last error. A `429` with `Retry-After` now waits as long as it asks, up to 5 minutes. Events dropped from a full queue are recorded under their own kind, not the kind of the event delivered before. See [How delivery works](docs/notifications.md#how-delivery-works).
- The audit page's By column broke `tester (dev)` over three lines at 1280 px when other columns were long. A principal and its person id now keep to one line each.
- `writ serve --check` on the first start after an upgrade printed `notify: delivery counts not read: control database operation failed (SQLSTATE 42P01)`, because it reads the control database before `writ serve` migrates it and migration 0020's table wasn't there yet. It now prints `notify: delivery counts appear after writ serve migrates the control database`, and the check still passes.
- A plan that changed nothing was `approved` when no approval rule matched it, so the control UI offered its apply command, said its author could not approve it, and counted it among the approved plans of its stack in the sidebar and the overview, while `writ plan --remote` said it had no change to apply. Its apply ran OpenTofu for nothing and superseded every other live plan of the `stack@env`. It is now `no-changes`, above. `writ plan --remote` no longer says a plan whose only change is an output has no change to apply.
- `tofu show` and `tofu apply` read the saved plan from the run's scratch directory, which every process of the run may write. OpenTofu 1.13.9 starts no provider for `show` of a saved plan it wrote, because the plan holds the providers' schemas, but it starts every provider for a saved plan without them, and such a provider could replace the file after `show` read it: Writ then sealed, or `tofu apply` applied, a saved plan other than the one the plan document and policy came from. Writ now reads the saved plan as soon as `tofu plan` exits, and `show` and `apply` read it from a sealed in-memory file that no process can change. See [Plan to apply](docs/plan-to-apply.md#2-isolated-planning-and-masking).
- A team's `writ serve` that runs as a user other than root, as the NixOS module and [Run isolation and egress](docs/run-isolation.md) set it up, failed every OpenTofu run with `fork/exec /proc/self/exe: permission denied`. Making the run's scratch directory as the provider uid left writ not dumpable, and the kernel then refused writ the uid map of the run's user namespace. Writ now makes itself dumpable while it starts a run's filesystem view, and not dumpable again right after. A provider or the `writ serve --check` probe that starts as a provider uid waits until then, because that start marks writ not dumpable too.
- `writ serve --dev` took an approval of a kept speculative plan, which the control UI never offers. Every control plane now refuses it with HTTP 409 and class `state`, as it refuses a drift plan; a team's control plane answered 400 and class `usage` before.
- A plan showed `(sensitive)` for the token settings of an auth method, such as `token_locality`, `max_token_ttl`, and `token_name_format` of `nomad_acl_auth_method`, because the mask hides every attribute whose name contains `token`. A name that ends in one `token` and a token setting, as [rule 3](docs/secrets.md#rule-3-names) lists, is no longer masked for its name. Its value is still masked where it is marked or holds a secret the mask learned.
- The note of an expired plan set a space before its full stop.
- The current stack in the sidebar, set in bold, wrapped its note onto a second line where the other stacks did not.
- A provider error or resource address that quoted the AWS role credentials the credential endpoint served a run kept the secret access key and session token in the stored plan or apply, because the mask knew only the endpoint's token. Each run's mask now knows the secret of every set of credentials the endpoint assumed for the run, refreshes included, on plans, refused plans, applies, index refreshes, and adoptions on S3. Those credentials aren't sealed into a state's secret set.
- A refused plan on S3 read and opened every secret set of the `stack@env` before the mask checked its 4 MiB limit. It now reads them one at a time, counts each secret once, and fails the plan when they pass the limit.
- A plan of a stack on S3 that tofu refused, as for a permission the plan role lacks, kept only `tofu plan exited with code 1`. It now keeps each diagnostic's summary and place, swept by a mask that knows every secret set `writ serve` keeps for the stack, with each instance key quoted once or twice shown as `["(sensitive)"]`.
- A sign-in through the browser that began while a `writ login` device login waited for its token read the provider's client config as the device login wrote to it, a data race.
- The docs for the control UI's sign-in and the `people` issuer now say that `writ login` through a browser needs `http://127.0.0.1/callback` as a redirect URI.

## 0.1.0 - 2026-11-17

The first release. Writ is a control plane for OpenTofu that you host yourself. It runs OpenTofu 1.13.9, reads repositories from GitLab, and gets cloud credentials from AWS roles. The release has static binaries for Linux and macOS on amd64 and arm64, signed with minisign key `D2D9A37AF1098999`, and the image `ghcr.io/mr-karan/writ:0.1.0`. The macOS binaries have not yet run on a Mac.

### The control plane

- `writ serve` plans the OpenTofu stacks of a Git repository by commit, from GitLab or, under `writ serve --dev`, from a local repository. It keeps the masked plan to show and the saved plan to apply, sealed with AES-256-GCM under the environment's key.
- `writ serve --dev` runs the same control plane for one person on loopback, with SQLite.
- A team's `writ serve` keeps its records and the state it serves in Postgres, signs people in with OIDC through `writ login` or the control UI, signs CI jobs in with their OIDC tokens, and has teams, grants, an audit log, rate limits, and time limits.
- The `http` state backend, sealed and versioned, where a plan's token can only read. A stack can instead keep its own `backend "s3"`, with a plan role that cannot write the bucket and an apply role for approved applies, from the credential broker's AWS roles.
- The state index of what each stack manages, `writ state adopt` for a state that `writ serve` did not write, and drift checks on a schedule with a `drift` block.

### Approvals and applies

- An approval names one plan id, a SHA-256 over the masked plan, the saved plan, the commit, the stack, and the environment. The apply runs that sealed saved plan.
- Approval rules by stack, environment, and risk class. The author's approval does not count, and a CI job that a person started counts as that person.
- A plan that a newer plan replaced, or whose state moved, is refused. `--override` applies without approvals, with a recorded reason, for a person with `override`.
- `writ apply --remote --merged` applies, after a merge, the approved plan whose sources equal the merged commit's.
- A GitLab CI component that plans each merge request, blocks the merge until each plan has its approvals, and applies after the merge, and `writ ci gitlab` to print its lines. No real GitLab instance has run it yet.

### Secrets and isolation

- One mask, `internal/mask`, over everything `writ serve` stores or shows: OpenTofu's sensitive marks, a sweep by value in plain, URL, JSON, hex, and base64 forms, names such as `password`, and an allow-list of keys. `just verify-mask` tests it with two canary secrets.
- On a team's `writ serve`, each `tofu` process runs as its own uid in new user, mount, and pid namespaces, on a root that holds only its run's files, with no capabilities. Module sources pass an allow-list, and `init` gets no cloud credential.

### Policy

- Rego policy sets in the server's config judge each masked plan when it is made and again before its apply. A mandatory set's deny refuses the plan, and nothing overrides it. `just policy-parity` requires the same verdicts from `conftest`.

### Console to code

- `writ import bulk` writes `resource` and `import` blocks for existing objects, read through their provider, with references in place of literal ids and `for_each` for objects of one shape.
- `writ import accept` passes only a plan that imports exactly those objects and changes nothing else, apart from a named list of provider-only settings.

### Agents

- `writ mcp` serves Model Context Protocol tools that plan a commit and read plans, runs, drift, the state index, and the policy. No tool applies or approves.
- `writ agent init` installs the writ skill into a repository.

### Packaging

- `--json` on every command but `serve`, `mcp`, `ci`, and `help`, with one versioned document on stdout.
- Static binaries for Linux and macOS on amd64 and arm64, a `writ serve` container image with OpenTofu 1.13.9, an install script that checks a minisign signature, a Nix flake with a NixOS module, and reproducible builds. `just release-dry-run` builds them all, signed with a throwaway key.
